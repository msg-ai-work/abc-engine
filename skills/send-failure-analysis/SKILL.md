# 발송 실패 분석

## 목적
발송 실패를 `요청수신 → Validation/라우팅 → Queue → Consumer → 외부 발송 → 결과처리`로 나누고 최초 실패 구간과 영향 범위를 식별한다.

## 입력
- 발생시간/환경/채널
- 비식별 Request 또는 Message ID
- 내부 상태/결과코드
- 관련 Log/Metric 요약
- 최근 배포·설정·트래픽 변화

## 절차
1. 요청이 Gateway에 정상 수신됐는지 확인한다.
2. Validation/라우팅과 Queue 적재 성공 여부를 확인한다.
3. Consumer가 요청을 가져갔는지 확인한다.
4. 외부 이통사/연계 요청 전송 여부와 응답을 확인한다.
5. 외부 응답과 내부 결과코드 Mapping을 분리해 본다.
6. 단건/고객/채널/전체 중 영향 범위를 좁힌다.
7. 최근 변경과 시간적 상관관계를 확인한다.

## 판단 기준
| 관찰 | 우선 원인 후보 |
|---|---|
| 요청 자체가 없음 | 고객/상위 연계 또는 수신 구간 |
| Queue 적재 전 실패 | Validation/라우팅/내부 처리 |
| Queue 적재 후 Consumer 미처리 | Consumer/Kafka/처리 용량 |
| 외부 요청은 성공, 실패 응답 수신 | 이통사/외부 정책 또는 요청 데이터 |
| 외부 성공인데 내부 실패 | 결과 Mapping/후처리 |

## 대표 Case
> 아래는 Skill 검증용 비식별 대표 사례이며 실제 고객 장애 기록이 아니다.

**현상:** RCS 요청은 Gateway에 수신되지만 결과가 실패로 증가한다. Queue Lag은 정상이고 외부 요청 로그까지 존재한다.

**분석:** 내부 Queue/Consumer보다 `외부 응답 코드 → 내부 결과코드 Mapping`과 외부 응답 원문(민감정보 제외)을 우선 확인한다. 외부 요청까지 정상이라는 근거 없이 내부 엔진 장애로 단정하지 않는다.

## 출력
- 영향 범위
- 최초 실패 구간
- 확인 근거
- 원인 후보와 신뢰도
- 추가 확인 항목
- 임시조치/근본조치 구분

## Human Gate
재처리, 트래픽 전환, 운영 설정 변경은 담당자 승인 후 수행한다.

## 금지사항
실제 메시지 원문, 전화번호, Credential을 Skill/Eval/Git에 저장하지 않는다.
